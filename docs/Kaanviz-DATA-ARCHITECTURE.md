# KaanViz Data Architecture

**Status:** Planning / Pre-Implementation  
**Purpose:** Define how data moves through KaanViz from source ingestion to validated analytical datasets and query results.

---

# 1. Data Architecture Principle

KaanViz treats data as a controlled analytical lifecycle:

```text
Source
  ↓
Ingestion
  ↓
Raw Data
  ↓
Profiling
  ↓
Type Understanding
  ↓
Preparation
  ↓
Validation
  ↓
Processed Dataset Version
  ↓
Analytical Query
  ↓
Analysis Result
  ↓
Visualization / Dashboard / AI
```

The most important rule is:

> **Raw source data is immutable; all analytical changes happen through explicit versions and deterministic transformations.**

This follows the existing KaanViz project architecture, which separates raw source data, processed Parquet data, metadata, profiling, preparation, modeling, and analytics.

---

# 2. Data Layers

KaanViz should conceptually maintain four major data layers:

```text
Layer 1 — Source / Raw
Layer 2 — Metadata / Profile
Layer 3 — Processed Analytical Data
Layer 4 — Query / Analysis Results
```

### Layer 1 — Raw

Original uploaded or fetched source.

### Layer 2 — Metadata

Information describing the data.

### Layer 3 — Processed

Validated analytical representation.

### Layer 4 — Results

Bounded outputs generated by analytical queries.

---

# 3. Workspace Data Boundary

Every dataset belongs to a Workspace.

```text
Workspace
   ↓
Data Source
   ↓
Dataset
   ↓
Dataset Versions
```

A dataset from Workspace A must never accidentally become available to Workspace B.

Workspace authorization is enforced at the API/application layer, while foreign keys preserve the structural relationship in PostgreSQL.

---

# 4. Data Source vs Dataset

KaanViz distinguishes:

```text
Data Source
```

from:

```text
Dataset
```

### Data Source

Describes where the data comes from.

Examples:

```text
orders.csv
PostgreSQL
Snowflake
S3
API
```

### Dataset

Describes the analytical object created from that source.

Example:

```text
Source:
orders.csv

Dataset:
Orders
```

This separation allows future connectors without redesigning the analytical pipeline.

# 8. Raw Storage

Raw data should be stored separately from PostgreSQL metadata.

Conceptually:

```text
Storage
│
└── workspace/{workspace_id}/
      └── datasets/{dataset_id}/
            └── raw/
                  └── source file
```

The exact physical path convention is an implementation decision.

The important architectural rule is that raw storage is immutable.

---

# 9. Raw Data Immutability

Once a source has been ingested:

```text
Raw Source
    ↓
READ-ONLY analytical source
```

Preparation must never modify the original source file.

Instead:

```text
Raw
 ↓
Transformation
 ↓
New Version
```

This provides reproducibility and traceability.

---

# 10. Dataset Identity

A dataset represents the logical analytical object.

Example:

```text
Dataset
Name: Orders
Source: orders.csv
Workspace: E-Commerce Analytics
```

The dataset can have multiple versions.

```text
Orders
 ├── v1 Raw
 ├── v2 Prepared
 └── v3 Validated
```

---

# 11. Dataset Versioning

A version represents a specific analytical state.

Conceptually:

```text
Dataset
   │
   ├── Version 1
   │     └── Raw
   │
   ├── Version 2
   │     └── Cleaned
   │
   └── Version 3
         └── Validated
```

Each version should be independently identifiable.

---

# 12. Version Lineage

Versions form a lineage graph, normally a parent-child chain:

```text
v1
 ↓
v2
 ↓
v3
```

A version should know its immediate parent where applicable.

This allows the system to explain:

```text
How did this dataset become this version?
```

---

# 13. Version Storage

Processed versions should use the analytical storage format specified by the project:

```text
Parquet
```

Conceptually:

```text
Raw Source
   ↓
Processing
   ↓
Parquet Version
```

Parquet provides an efficient representation for analytical workloads.

---

# 14. Processed Storage Layout

Conceptually:

```text
storage/
└── workspace/{workspace_id}/
    └── datasets/{dataset_id}/
        ├── raw/
        │   └── source.csv
        │
        └── versions/
            ├── v1/
            │   └── data.parquet
            ├── v2/
            │   └── data.parquet
            └── v3/
                └── data.parquet
```

The exact directory/object-key design can be changed during implementation.

The logical separation should remain.

---

```text

       ↓
Profiler

Dataset Profile
```

Profiling can calculate:

```text
Column count

Quality indicators
```

### Column-level

```text

Physical type
Semantic type
Null count
Distinct count

Min/max
```

Only applicable statistics should be generated for each data type.

```text
Month coverage
```

AI can later explain the results.

Examples:

```text

Category

```


---

# 20. Type Inference

Type inference flow:

```text
Raw Column
    ↓
Physical Type Detection
    ↓
Value Inspection
    ↓
Semantic Type Inference
    ↓
Profile
```

Inference must remain explainable.

Example:

```text

string

```

---

# 21. User Type Override

Users may override inferred semantic types.

```text
Inferred Type
    ↓
User Review
    ↓
Override
    ↓
Validation
    ↓
New / Updated Dataset Version
```

A user decision should not silently rewrite the raw source.

```text
Transformation Specification
        ↓
Validation
        ↓
```

```text

Duplicate handling

```

# 24. Column Operations

Examples:


Conceptual transformation:

```json

  "operation": "rename_column",
  "source": "customer_name",
  "target": "customer"
}
```

The transformation engine executes the operation.

# 26. Missing-Value Operations

# 27. Duplicate Operations

# 28. Date Operations

Potential operations:

```text
Parse date
```

---

# 29. Numeric Operations

Potential operations:

```text
Convert numeric type

```

The exact transformation catalog should be finalized during the implementation specification.

---

# 30. Row Filtering

Rows can be filtered using structured conditions.

Example:

```text
status = "Delivered"
```

Conceptually:

```json
{
  "operation": "filter_rows",
  "condition": {
    "field": "status",
    "operator": "equals",
    "value": "Delivered"
  }
}
```

Arbitrary executable expressions should not be accepted as a substitute for a validated transformation specification.

---

# 31. Transformation Lineage

Each preparation action creates a traceable record:

```text
Dataset Version A
       ↓
Transformation
       ↓
Dataset Version B
```

Example:

```text
Orders v1
   ↓ Convert order_date → Date
Orders v2
   ↓ Remove duplicate order_id
Orders v3
```

This gives KaanViz an explainable preparation history.

---

# 32. AI Preparation Recommendations

AI may recommend transformations.

Example:

```text
AI Recommendation

I found 1,245 duplicate order IDs.

Suggested action:
Remove duplicate order IDs.

[ Review ] [ Apply ] [ Ignore ]
```

AI does not execute arbitrary transformations directly.

The flow is:

```text
AI
 ↓
Structured Transformation Recommendation
 ↓
Validation
 ↓
User Approval
 ↓
Deterministic Transformation Engine
 ↓
New Dataset Version
```

---

```text
Validated Parquet
       ↓
DuckDB / Polars
       ↓
Analysis
       ↓
Result
```

Potential operations:

```text

Aggregation
Grouping

Joining

Time-series analysis
Correlation

```

---

# 36. DuckDB Role

DuckDB should act as an analytical query engine over the processed data.

Conceptually:

```text
Parquet
   ↓
DuckDB
   ↓
SQL / analytical query
   ↓
Result
```

It should be used to avoid loading unnecessarily large datasets into application memory.

---

# 37. Polars Role

Polars can support:

```text
Data transformation
Data processing
Column operations
Profiling
Analytical workflows
```

The exact boundary between DuckDB and Polars should be determined by workload and implementation simplicity.

The two should not duplicate responsibility unnecessarily.

---

# 38. Pandas Role

Pandas may be used where it provides useful compatibility or convenience, particularly for Python-assisted analytical workflows.

It should not become the mandatory processing engine for every dataset.

---

# 39. Browser Data Boundary

The browser should receive:

```text
Profile summaries
Preview samples
Aggregated analysis results
Visualization-ready results
```

The browser should generally not receive:

```text
Entire large raw dataset
Entire large Parquet dataset
```

This protects performance and memory usage.

---

# 40. Dataset Preview

Preview requests should be bounded.

Conceptually:

```text
Dataset
 ↓
Preview Request
 ↓
Limited sample
 ↓
Browser
```

The backend must enforce limits rather than trusting the client.

---

# 41. Analytical Result Boundary

For example:

```text
10 million rows
       ↓
GROUP BY month, category
       ↓
240 rows
       ↓
Browser
```

The browser can render the 240 analytical results efficiently.

---

# 42. Analysis Result Storage

Analysis results may be:

```text
Returned immediately
Cached temporarily
Stored as reusable result metadata
Stored externally if large
```

The exact strategy depends on result size and performance requirements.

PostgreSQL should not automatically store every large result as row-level metadata.

# 55. Performance Principles

### Do

- Profile using efficient columnar operations.
- Use Parquet for processed analytical data.
- Push aggregation toward DuckDB/Polars.
- Bound previews.
- Avoid unnecessary data transfer.
- Cache/reuse safe analytical results where useful.

### Avoid

- Loading millions of rows into React.
- Sending entire datasets through JSON APIs.
- Running expensive analysis synchronously without reason.
- Recomputing identical analytical results unnecessarily.

---

KaanViz should distinguish:

```text
Raw Fact

AI Interpretation

```

# 57. Data Security

Data should be treated as untrusted throughout ingestion and AI context construction.

Important boundaries:

```text
Upload validation
      ↓
Storage
      ↓
Parsing
      ↓
Transformation
      ↓
Analytics
      ↓
AI context
```

No uploaded cell should automatically be trusted as executable instructions.

---

# 58. Export Considerations

```text
Export Processor
       ↓

```

# 61. What AI Must Never Do Directly

AI must not directly:

```text
Modify raw files
Execute arbitrary Python
Execute arbitrary SQL without validation
Overwrite dataset versions
Delete rows without a controlled transformation
Create unapproved relationships
Generate arbitrary frontend code
Bypass Workspace authorization
```

AI produces structured intent/recommendations that pass through application validation.

# 64. Final Data Architecture Principle

> **KaanViz should preserve the original source, transform data through explicit reproducible versions, validate before analytical use, execute computation in the analytical engine, and expose only the appropriate results to visualization, dashboards, and optional AI.**

This creates a traceable path:

```text
Raw Data
   ↓
Trusted Dataset Version
   ↓
Deterministic Analysis
   ↓
Visualization / Dashboard
   ↓
AI Interpretation
```

The user remains in control throughout the lifecycle.
